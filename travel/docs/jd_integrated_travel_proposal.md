# 京东商品 + 商旅一体化方案提案

## 项目概述

本方案面向京东企业客户场景，目标是在现有商品能力与商旅能力基础上，形成一套可统一展示、统一销售、统一交付的一体化解决方案。

本方案不以“重做一套独立商旅系统”为目标，而是以“整合既有能力、补齐企业关键短板、形成客户可落地方案”为目标。重点补齐的能力包括：
- 商品与商旅的一体化交付方式
- 企业审批能力
- 差旅管控能力
- 关键交易与履约流程闭环

## 1. 项目背景与项目定义

京东当前面向企业客户的两类能力分属不同团队和系统：
- 锦礼/商品能力一套
- 商旅/酒店能力一套

客户侧的真实诉求不是分别采购和使用两套系统，而是希望以统一入口获得“商品 + 酒店/商旅”的一体化能力。

我们此前已经具备与京东 VOP 体系的对接经验，因此本次工作的目标不是重建京东既有底座，而是在现有能力基础上完成商品与商旅能力的整合交付，并补齐企业客户场景中关键但当前相对薄弱的能力模块，尤其是：
- 企业审批
- 差旅管控
- 核心流程闭环

因此，本项目本质上是一次面向企业客户交付的一体化方案整合与增强，而不是单一商旅子系统的孤立建设。

## 2. 现状系统、既有能力与主要短板

### 2.1 京东现有能力

- 商品能力已有独立系统与交付链
- 商旅能力已有独立系统与交付链
- 面向企业客户已有一定商旅客户基础
- 内部销售与客户交付链路已存在

### 2.2 我们已有能力

- 已有 VOP 对接经验
- 已有可验证的 Travel 方案原型
- 已沉淀审批、差标、订单与履约相关建模和页面能力

### 2.3 当前主要短板

- 商品与商旅仍是分开的系统与交付方案
- 企业审批与差旅管控能力相对薄弱
- 面向客户的一体化产品表达不足
- 后续客户化交付缺少统一的平台底座与标准边界

本次工作的价值，不是替京东推翻重做底座，而是在既有底座之上补一层可销售、可交付、可扩展的企业差旅方案层。

## 3. 本次方案目标与交付边界

### 3.1 本次目标

- 形成商品 + 商旅的一体化方案底座
- 补齐企业审批、差旅管控、关键流程闭环能力
- 形成可统一展示、统一销售、统一交付的解决方案骨架
- 为后续客户项目实施提供复用底座

### 3.2 本次不包含

- 不一次性覆盖所有客户的个性化需求
- 不一次性完成所有 OA / 财务 / 报销 / ERP 深度联调
- 不一次性覆盖所有商旅品类与所有供应商
- 不把后续客户实施工作隐含打包进本次平台建设范围

这次交付的重点是平台能力建设，而不是所有客户场景的完整落地。

## 4. 方案结构与能力补齐点

### 4.1 方案结构

整体方案建议分成四层：
- 商品能力层
- 商旅能力层
- 企业审批/差标/管控层
- 宿主接入层与客户系统集成层

### 4.2 我们的方案设计

从方案设计角度看，这次不是单一系统，而是“宿主能力 + 差旅业务层 + 企业流程层 + 集成桥接层”的组合。

建议对外用下面这个结构描述：

- **宿主接入层**
  - 对接京东现有商品体系、商旅体系以及既有 VOP 接入能力
  - 负责统一入口、统一客户侧交付方式、统一外部接口暴露
- **Travel 业务层**
  - 承担搜索、报价、下单、改签、退票、履约等差旅核心流程
  - 对酒店、机票、火车、度假等品类形成统一业务模型
- **企业流程层**
  - 在通用审批能力之上补齐差标、超标策略、审批串联、企业管控
  - 解决京东现有商旅能力中对企业客户最关键的短板
- **集成桥接层**
  - 连接宿主、审批、支付、供应商和履约链路
  - 把京东既有能力和我们新增能力真正串成一个可交付方案

换句话说，这次不是只做“一个 travel 系统”，而是做一个能嵌入京东现有体系、又能面向企业客户交付的一体化方案层。

### 4.3 本次重点补齐能力

- 商品与商旅的一体化入口与流程组织
- 差旅审批能力
- 差标与超标策略
- 改签、退票、履约等企业差旅关键流程
- 面向企业客户的统一方案表达

### 4.4 对京东价值

- 把现有商品能力与商旅能力打包成统一方案
- 补强现有商旅能力中最影响企业成交的短板
- 形成后续客户项目可复用、可扩展的平台基础

### 4.5 当前方案建设范围概览

为便于评估本次平台建设范围，当前方案可按下面理解：

- **Travel 核心模型：15 个实体**
  - 静态主数据 5 个
  - Offer 4 个
  - 交易/履约 2 个
  - 企业差旅增强实体 4 个
- **前端业务页面：68 个**
  - 管理端 44 个
  - 用户端 24 个
- **集成桥接：8 个**
  - 负责宿主上下文、支付、供应商提交、出票/取消等关键桥接

这说明本项目不是轻量级页面拼装，而是一套具备完整业务轮廓的企业差旅方案底座。对外沟通时，不建议展开到“多少页面、多少实体”的技术细节，而建议统一表述为：本次建设范围覆盖方案底座、核心流程、审批管控与关键集成能力。

## 5. 本次交付清单、交付物与阶段划分

### 5.1 本次交付清单

- 平台代码与模型
- 核心页面与流程
- 商品/商旅/审批相关 bridge 与运行时接入
- 提案与实施文档
- 测试、验收与演示材料

### 5.2 建议阶段划分

1. 方案收口与模型确认
2. 核心平台能力补齐
3. 页面与流程打通
4. 演示版本与验收交付

### 5.3 交付结果定义

首期交付应被定义为：
- 一套可演示、可继续客户化实施的平台底座
- 而不是一次性包完所有最终客户定制项

## 6. 商务合作方式与报价口径

### 6.1 合作方式建议

建议采用两阶段合作模式：

第一阶段：
- 收取平台建设费
- 完成一体化方案底座建设

第二阶段：
- 京东后续每落一个具体客户
- 再按客户需求单独评估、单独报价、单独实施

### 6.2 报价说明

本次建议按“平台建设与交付能力”口径报价，而不是按单纯源码或页面开发口径报价。

后续客户项目应单独计费，包括但不限于：
- 客户化页面与流程
- OA / 财务 / 报销 / ERP 集成
- 组织权限与审批规则定制
- 特定供应商与渠道对接

### 6.3 报价留白

本节留作后续商务确认：

- 平台建设费：_______
- 交付阶段划分：_______
- 后续客户项目计费方式：_______
- 维护与升级方式：_______

### 6.4 商务边界

- 平台建设费对应平台底座与方案能力
- 客户项目费用对应客户实施与定制交付
- 平台升级与客户项目实施应拆分管理、拆分报价

## 7. 非目标、风险与后续客户化实施方式

### 7.1 非目标

- 不在首期覆盖全部客户场景
- 不在首期完成所有深度系统集成
- 不承诺无限制客户化修改

### 7.2 风险

- 京东内部商品与商旅系统边界可能继续调整
- 企业客户审批/财务流程差异较大
- 真实供应商联调与企业系统联调会拉高项目复杂度

### 7.3 后续客户化实施方式

建议采用“平台底座 + 客户项目”的长期合作方式：

- 平台层负责统一能力沉淀
- 客户层按具体需求实施
- 后续新增能力、变更需求与深度集成通过新项目或新阶段承接

这样可以同时保证：
- 首期边界清晰
- 后续扩展有路径
- 商务模型可持续

## 8. 建议下一步

建议下一步按以下顺序推进：

1. 先对本提案的项目定义、交付范围与商务边界达成一致
2. 再收敛首期平台建设范围
3. 最后再进入报价与实施排期讨论

这样可以避免在范围未清晰前直接谈价格，导致后续范围与交付责任失真。
