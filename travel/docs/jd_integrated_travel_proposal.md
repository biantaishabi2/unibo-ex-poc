# 京东商品 + 商旅一体化方案提案

## 项目概述

本方案面向京东企业客户场景，目标是在现有商品能力与商旅能力基础上，形成一套可统一展示、统一销售、统一交付的一体化解决方案。

本方案不以“重做一套独立商旅系统”为目标，而是以“整合既有能力、增强企业场景能力、形成可落地方案”为目标。重点建设内容包括：
- 商品与商旅的一体化交付方式
- 企业审批能力
- 差旅管控能力
- 关键交易与履约流程闭环

## 1. 项目背景与项目定义

京东当前面向企业客户的两类能力分属不同团队和系统：
- 锦礼/商品能力一套
- 商旅/酒店能力一套

客户侧的真实诉求不是分别采购和使用两套系统，而是希望以统一入口获得“商品 + 酒店/商旅”的一体化能力。

我们此前已经具备与京东 VOP 体系的对接经验，因此本次工作的目标不是重建京东既有底座，而是在现有能力基础上完成商品与商旅能力的整合交付，并完善企业客户场景中关键能力模块，尤其是：
- 企业审批
- 差旅管控
- 核心流程闭环

因此，本项目本质上是一次面向企业客户交付的一体化方案整合与增强，而不是单一商旅子系统的孤立建设。

## 2. 现状基础与建设重点

### 2.1 京东现有能力

- 商品能力已有独立系统与交付链
- 商旅能力已有独立系统与交付链
- 面向企业客户已有一定商旅客户基础
- 内部销售与客户交付链路已存在

### 2.2 实施基础

- 已有 VOP 对接经验
- 已有可验证的差旅方案原型
- 已沉淀审批、差标、订单与履约相关能力基础

### 2.3 当前建设重点

- 商品与商旅仍是分开的系统与交付方案
- 企业审批与差旅管控能力仍有进一步完善空间
- 面向客户的一体化产品表达不足
- 后续客户化交付缺少统一的平台底座与标准边界

本次工作的价值，不是替京东重建底座，而是在既有底座之上形成一套可销售、可交付、可扩展的企业差旅解决方案。

## 3. 本次方案目标与交付边界

### 3.1 本次目标

- 形成商品 + 商旅的一体化方案底座
- 完善企业审批、差旅管控、关键流程闭环能力
- 形成可统一展示、统一销售、统一交付的解决方案骨架
- 为后续客户项目实施提供复用底座

### 3.2 本次不包含

- 不一次性覆盖所有客户的个性化需求
- 不一次性完成所有 OA / 财务 / 报销 / ERP 深度联调
- 不一次性覆盖所有商旅品类与所有供应商
- 不把后续客户实施工作隐含打包进本次平台建设范围

这次交付的重点是平台能力建设，而不是所有客户场景的完整落地。

## 4. 方案结构与能力建设重点

### 4.1 方案结构

整体方案建议分成四个部分：
- 商品能力部分
- 商旅能力部分
- 企业审批/差标/管控部分
- 外部接入与客户系统集成部分

### 4.2 我们的方案设计

从方案设计角度看，这次不是单一系统，而是“接入能力 + 差旅业务能力 + 企业流程能力 + 集成能力”的组合。

建议对外用下面这个结构描述：

- **接入层**
  - 对接京东现有商品体系、商旅体系以及既有 VOP 接入能力
  - 负责统一入口、统一客户侧交付方式、统一外部接口暴露
- **差旅业务层**
  - 承担搜索、报价、下单、改签、退票、履约等差旅核心流程
  - 对酒店、机票、火车等品类形成统一业务模型
- **企业流程层**
  - 在通用审批能力之上完善差标、超标策略、审批串联、企业管控
  - 提升面向企业客户的差旅管理能力
- **集成层**
  - 连接现有业务系统、审批、支付、供应商和履约链路
  - 将京东既有能力和本次建设能力串联成统一方案

换句话说，这次不是单做一个差旅子系统，而是建设一个能嵌入京东现有体系、又能面向企业客户交付的一体化方案层。

### 4.3 本次重点建设能力

- 商品与商旅的一体化入口与流程组织
- 差旅审批能力
- 差标与超标策略
- 改签、退票、履约等企业差旅关键流程
- 面向企业客户的统一方案表达

### 4.4 对京东价值

- 把现有商品能力与商旅能力打包成统一方案
- 增强现有商旅能力中面向企业客户的关键环节
- 形成后续客户项目可复用、可扩展的平台基础

### 4.5 当前方案建设范围概览

为便于评估本次建设规模，建议从“业务对象、操作能力、业务规则、关键流程”四个维度理解本次范围。

#### 4.5.1 业务对象范围

本方案覆盖的核心业务对象包括：

- **基础资料类**
  - 酒店
  - 房型
  - 航司
  - 舱位
  - 静态码映射
- **报价类**
  - 酒店报价
  - 机票报价
  - 火车票报价
- **交易类**
  - 差旅订单
  - 改签单
  - 退票/退订单
- **履约类**
  - 履约记录
- **企业管控类**
  - 差旅政策
  - 差标校验记录

从业务对象角度看，本次并不是只覆盖“下单”一个点，而是覆盖从基础资料、报价、交易、履约到企业管控的完整链路。

#### 4.5.2 操作能力范围

本方案覆盖的不是简单展示页面，而是一整套业务操作能力，包括：

- 基础资料的查询、创建、编辑、启用、停用
- 报价的查询、上架、下架、失效处理
- 订单的创建、确认、支付、状态流转
- 改签单、退票单的申请、审核、完成、拒绝
- 差旅政策的配置、启用、停用
- 差标校验记录的查询、审核与关联审批

也就是说，本次范围不仅包含常规的新增、查询、编辑与维护能力，还包含真实业务流程中的关键操作能力与状态流转能力。

#### 4.5.3 业务规则与关键操作范围

本方案的核心复杂度不只在界面数量，更在于业务规则和关键操作链路，主要包括：

- 报价有效性与上下架规则
- 订单创建、支付、确认、取消、履约等动作链路
- 改签与退票的申请、费用计算、状态流转
- 差标匹配、超标识别、超标原因填写、审批触发
- 审批通过后才允许后续关键动作继续执行
- 供应商提交、出票、取消、支付等外部动作桥接

如果从系统能力角度描述，本次范围既包括：
- 基础资料管理
- 关键业务操作
- 状态与流程流转
- 规则校验
- 外部系统调用

因此它不是简单的数据录入系统，而是一个具备完整业务操作语义的企业差旅方案。

#### 4.5.4 前端与流程范围

前端范围覆盖两类场景：

- **用户端**
  - 搜索
  - 详情
  - 预订
  - 支付确认
  - 订单查看
  - 改签
  - 退票
  - 出差申请
  - 审批查看
- **管理端**
  - 基础资料管理
  - 报价管理
  - 订单与履约管理
  - 差旅政策管理
  - 差标校验管理
  - 企业配置、审批规则、集成配置

因此，前端建设范围不只是若干孤立页面，而是完整覆盖用户侧交易闭环和管理侧运营闭环。

#### 4.5.5 集成范围

本方案还包括关键集成能力：

- 与现有商品体系和商旅体系的统一接入
- 与支付能力的衔接
- 与供应商侧下单、出票、取消、确认链路的衔接
- 与企业审批能力或外部审批系统的衔接

从交付范围看，本项目覆盖的不是单点功能，而是一套完整的企业差旅方案底座，范围包括业务对象、操作能力、业务规则、流程闭环与关键集成能力。

## 6. 商务合作方式与报价口径

### 6.1 合作方式建议

建议采用两阶段合作模式：

第一阶段：
- 收取平台建设费
- 完成一体化方案底座建设

第二阶段：
- 京东后续每落一个具体客户
- 再按客户需求单独评估、单独报价、单独实施

### 6.2 报价说明

本次建议按“平台建设与交付能力”口径报价。

后续客户项目应单独计费，包括但不限于：
- 客户化流程与界面
- OA / 财务 / 报销 / ERP 集成
- 组织权限与审批规则定制
- 特定供应商与渠道对接

### 6.3 报价留白

本节留作后续商务确认：

- 平台建设费：_______
- 交付阶段划分：_______
- 后续客户项目计费方式：_______
- 维护与升级方式：_______

### 6.4 商务边界

- 平台建设费对应平台底座与方案能力
- 客户项目费用对应客户实施与定制交付
- 平台升级与客户项目实施建议拆分管理、拆分报价

## 7. 非目标、风险与后续客户化实施方式

### 7.1 非目标

- 不在首期覆盖全部客户场景
- 不在首期完成所有深度系统集成
- 不承诺无限制客户化修改

### 7.2 风险

- 京东内部商品与商旅系统边界可能继续调整
- 企业客户审批/财务流程差异较大
- 真实供应商联调与企业系统联调会提升项目实施复杂度

### 7.3 后续客户化实施方式

建议采用“平台底座 + 客户项目”的长期合作方式：

- 平台层负责统一能力沉淀
- 客户层按具体需求实施
- 后续新增能力、变更需求与深度集成通过新项目或新阶段承接

这样可以同时保证：
- 首期边界清晰
- 后续扩展有路径
- 商务模型可持续

## 8. 建议下一步

建议下一步按以下顺序推进：

1. 先对本提案的项目定义、交付范围与商务边界达成一致
2. 再收敛首期平台建设范围
3. 最后再进入报价与实施排期讨论

这样可以避免在范围未清晰前直接谈价格，导致后续范围与交付责任失真。
